# 需求单：对外发布前的准备（自查 / 整改 / 清单 / 校对）

- id：`26.5.0-release-readiness`
- 档位：M
- 版本：不升（不动 `build.gradle.kts`）
- 提出：2026-11-03

## 一、目标（PM）

把"能不能对外发布 Orange"从一句感觉，变成一张**每条都带判据、能实际验证**的清单。
**发布动作本身一步都不做。**

用户 2026-11-03 23:37 原话：「在我确认授权发布前，只允许做正式发布前的准备工作，包括自查，整改，列出清单，校对清单。」

## 二、使用场景（PM）

- 用户想判断"现在到底离能发布还差什么"，不想听"差不多了"。
- 用户将来某天说"发吧"，能立刻照清单执行，而不必从头再查一遍。
- 换一个 session 接手，看清单就知道进度，不用读几百行日志。

## 三、不做什么（PM）

- 不建 Release、不改仓库可见性、不改品牌门面、不对外宣告。
- 不改 `release.sh`、不改 `.gitignore`、不动 `dist/`、不改版本号（上一轮动过又退回，这次不碰）。
- 不写 App 代码（"开源许可页"需编译验证，另立 S 档；本单只列条目）。

## 四、验收判据（QA 照此验）

1. 清单每条都有：判据、现状、证据、归属、是否阻塞。
2. **不存在"计划写成已完成"**：凡未实际验证的，状态必须是"未验"，不能写成"通过"。
3. 发现的问题要么已整改，要么写清为什么不整改（含代价）。
4. 校对环节必须真的改正错误，不能"复查无误"了事——本轮实际改了 4 处（其中 1 处是清单自己的统计错误）。
5. 对外零变化：远端 commit 不变、Releases 仍为空、仓库可见性不变。

## 五、方案（CTO）

产出 `docs/release/CHECKLIST.md`（主交付物）+ 两张单据。

状态只取五种，避免含糊：

| 记号 | 含义 |
|---|---|
| ✅ | 已实际验证通过，附证据 |
| ⚠️ | 需整改，我或用户能修 |
| ❓ | 需用户拍板 |
| ⛔ | 阻塞发布：不解决不能发 |
| ⬜ | 未验（条件不具备，如"需真发版才验得到"） |

分组：A 法务许可 / B 构建产物 / C 更新通道 / D 隐私联网 / E 权限 / F 品牌门面 / G 支持回滚 / H 发布动作。

## 六、风险与回滚

- 风险：把"准备"做成"发布"。对策：产出全是 `docs/` 下文档，无脚本行为改动、无版本号改动、不推送。
- 回滚：删 `docs/release/` 与两张单据，无副作用。

### 唯一的代码改动：删 `ACCESS_FINE_LOCATION`

- `app/src/main/AndroidManifest.xml`：删权限声明与 `hardware.location.gps` 的 uses-feature，留注释说明原因
- `tools/install.sh`：删 `pm grant … ACCESS_FINE_LOCATION` 那一行
- `app/src/main/java/app/orchard/tv/system/Diagnostics.kt`：删诊断串里的 `location=` 字段

**依据**：该权限只服务于"显示 Wi-Fi 名称"，且只由 `install.sh` 用 adb 授予——侧载用户从来没有过它，
所以删除对绝大多数用户零变化；`SystemState` 对 `<unknown ssid>` 本来就有过滤，取不到不崩。

4. 密钥备份能解出、指纹与原件一致（已验，见 QA）
