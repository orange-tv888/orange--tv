# 需求单：发版脚本收口：只提交该提交的、安装包自动重打

> PM 写前三段，CTO 写「方案」段。G1 过门后不再改前三段。

- id：`26.4.3-release-hardening`
- 档位：M
- 版本：不随 APK 发版（改的是开发工具 `tools/release.sh`，不影响装机包）
- 提出：2026-11-03

## 一、目标（PM）

让**发版这一步不再靠人记得住细节**，而不是每次发完都留一条"待办：安装包还没重打"。

## 二、使用场景（PM）

1. 26.4.2 发版时，`release.sh` 的 `git add -A` 把工作区里一张 1.1MB 的调试截图（`dist/shots/scroll-after-26.4.1.png`）一起提交进了发布提交。
2. 历史上至少有两次发完版才想起 `dist/orange-newtv-setup.zip` 里还是旧 APK，得再手动重打（11-01、11-02 各一次，26.4.2 这次是事后补的）。
3. 推送到 `ssh.github.com:443` 之后本地 `origin/main` 不更新，`git status` 一直显示"ahead by 3 commits"，容易误判没推上去。

## 三、不做什么（PM）

- 不改成交互式脚本（发版要能一口气跑完，不能停下来等人按回车）。
- 不动编译参数和签名逻辑（稳定，改坏代价太大）。
- 不引入新依赖（`zip` / `unzip` 系统自带够用）。
- 不做"自动写复盘"这种假自动化。

## 四、验收判据（PM，每条必须可验证）

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | `dist/shots/*`、`*.log`、`*.mp4`、`.DS_Store` 不会被提交，且脚本打印"被挡下"清单 | 造假的 `foo.log` 与 `dist/shots/x.png`，跑 `--check` 看清单 |
| 2 | 新增 `--check`：只体检、不编译、不提交、不推送 | 干净工作区跑退出码 0；版本号传错退出码非 0 |
| 3 | 版本号与 `build.gradle.kts` 不一致时直接失败，不进入编译 | `--check 26.9.9` 必须报错 |
| 4 | 三份 APK（构建产物 / `update/` / `dist/`）哈希不一致即失败 | 替换其中一份，看是否 die |
| 5 | `dist/newtv/payload/orange.apk` 自动换新并重打 `orange-newtv-setup.zip` | `unzip -l` 里的大小与时间戳是新包 |
| 6 | 推送成功后本地 `origin/main` 跟上，`git status` 不再显示 ahead | 推完 `git log origin/main -1` 是本条发布提交 |

## 五、方案（CTO，G1 填）

- 改动面：只有 `tools/release.sh`（外加 `docs/` 里三张单子）
- 关键取舍：
  - **拒绝清单而不是白名单**。白名单会在新增目录时漏提交，代价比多提交一张截图更大；用拒绝清单兜住"一看就不该进仓库"的几类，其余照旧。
  - **`--check` 复用正式流程的校验函数**，避免"体检通过、正式跑又挂"两套逻辑。
  - 安装包重打只用 `zip -q -X <zip> <entry>` 更新单个条目，不整包重压，保留其它文件的可执行位与时间戳。
- 风险：`release.sh` 是唯一发版通道，改错就发不出去。所以所有校验都加在**破坏性动作之前**（编译前、提交前、推送前）。
- 回滚：`git revert` 本条提交即可，脚本无状态。
- 测试点：见上面的六条判据。
